1Why data warehouses matter

பழைய தரவும் ஏன் தேவை?

இன்றைய விற்பனைப் பதிவு மட்டும் நீண்டகால வளர்ச்சியைக் காட்டாது. பல ஆண்டுகள், பல பிரிவுகளின் தகவலைச் சேர்த்து ஒப்பிட்டால் முடிவு எடுக்க உதவும். இதற்கான தனிச் சேமிப்புதான் Warehouse.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Data warehouse பல sources-ஐ clean/integrate/transform செய்து historical analysis-க்கு ஒரே consistent view தருகிறது. OLAP மூலம் detail/summarised levels-இல் interactive queries; mining மூலம் associations/classifiers/clusters. Warehouse அமைப்பதே preprocessing-க்கு உதவும்; warehouse வைத்திருப்பதால் data தானாக accurate அல்லது useful ஆகிவிடாது.

  • Data warehouses generalise and consolidate data in multidimensional space.
  • Building one involves data cleaning, data integration and data transformation, so it is an important preprocessing step for data mining.
  • They provide OLAP (On-Line Analytical Processing) tools for interactive analysis of multidimensional data at different granularities.
  • Mining functions such as association, classification, prediction and clustering can be integrated with OLAP to mine at multiple levels of abstraction.

So the data warehouse is an important platform for data analysis, OLAP and data mining.

  • தரவுக் கிடங்குகள் பல்பரிமாண வெளியில் தரவைப் பொதுமைப்படுத்தி ஒருங்குதிரட்டுகின்றன.
  • ஒன்றை உருவாக்குவதில், தரவுத் தூய்மைப்படுத்தல், தரவு ஒருங்கிணைப்பு, தரவு உருமாற்றம் அடங்குவதால், அது தரவுச் சுரங்கத்துக்கான முக்கிய முன்செயலாக்கப் படி.
  • பல்பரிமாணத் தரவை வெவ்வேறு நுணுக்க நிலைகளில் இடைவினையுடன் பகுப்பாய்வு செய்ய, OLAP (நிகழ்நிலைப் பகுப்பாய்வுச் செயலாக்கம்) கருவிகளை வழங்குகின்றன.
  • பல அருவாக்க நிலைகளில் சுரங்கம் செய்ய, தொடர்பு விதி, வகைப்படுத்தல், முன்னறிவிப்பு, குழுமமாக்கல் போன்ற சுரங்கச் செயல்பாடுகளை OLAP-உடன் ஒருங்கிணைக்கலாம்.

எனவே தரவுக் கிடங்கு தரவுப் பகுப்பாய்வு, OLAP, தரவுச் சுரங்கம் ஆகியவற்றுக்கான முக்கிய தளம்.

2What is a data warehouse?

Data warehouse எளிமையாக

பல மூலங்களிலிருந்து ஒருங்கிணைக்கப்பட்ட வரலாற்றுத் தகவலை ஆய்விற்காக வைத்திருப்பது Data warehouse. Subject-oriented, integrated, time-variant, non-volatile அதன் முக்கிய பண்புகள். நாளாந்தப் பதிவைத் திருத்தும் அமைப்பல்ல.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

Warehouse-இன் நான்கு பண்புகள்: subject-oriented — customer/sales போன்ற பொருளை மையமாக்குதல்; integrated — sources ஒரே codes/units; time-variant — historical periods; nonvolatile — analysis data பொதுவாக stable, transaction-style update அல்ல. Nonvolatile என்றால் warehouse ஒருபோதும் load/update ஆகாது என்று அர்த்தமில்லை. ETL மூலம் புதிய snapshots அல்லது records சேர்க்கப்படலாம்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

SITN: subject-oriented=customer/sales போன்ற analysis subject; integrated=ஒரே codes/units/meaning; time-variant=historical perspective; nonvolatile=day-to-day transaction போல தொடர்ந்து overwrite செய்யாமல் controlled load/refresh மற்றும் analysis. Nonvolatile என்றால் backup, recovery, concurrency தேவையில்லை என்பதல்ல. “5–10 years” course example; எல்லா warehouses-க்கும் fixed retention இல்லை.

Data warehousing provides architectures and tools for business executives to systematically organise, understand and use their data to make strategic decisions. Many firms have spent millions building enterprise-wide data warehouses.

  • A data warehouse is a database maintained separately from the organisation's operational databases.
  • It allows integration of a variety of application systems.
Inmon's definition — learn it word for word

According to William H. Inmon: "A data warehouse is a subject-oriented, integrated, time-variant, and nonvolatile collection of data in support of management's decision-making process."

These four keywords are what set a data warehouse apart from relational DBs, transaction processing systems and file systems:

Keyword Meaning Example
Subject-oriented Organised around major subjects (customer, supplier, product, sales). Focuses on modelling and analysis for decision makers, not day-to-day operations A "Sales" subject area rather than an "invoice entry" app
Integrated Built from multiple heterogeneous sources (relational DBs, flat files, online transaction records). Cleaning and integration ensure consistent naming, encoding, attribute measures Gender stored as M/F everywhere, not M/F in one source and 1/0 in another
Time-variant Stores data from a historical perspective (past 5–10 years). Every key structure contains an element of time, implicitly or explicitly Sales per month for the last 8 years
Nonvolatile Stable analytical data maintained by controlled loads and refreshes rather than ordinary operational transactions. Backup, recovery and safe concurrent reads/loads can still be necessary Nightly load, then read-only queries
Memory hook: "SITN"

Subject · Integrated · Time-variant · Nonvolatile. Say: "Sales In Time, Never changed."

தரவுக் கிடங்காக்கல், வணிக நிர்வாகிகள் தங்கள் தரவை முறையாக ஒழுங்கமைத்து, புரிந்துகொண்டு, உத்திசார் முடிவுகளுக்குப் பயன்படுத்துவதற்கான கட்டமைப்புகளையும் கருவிகளையும் வழங்குகிறது. பல நிறுவனங்கள் நிறுவனம் முழுவதற்குமான தரவுக் கிடங்குகளை உருவாக்க மில்லியன் கணக்கில் செலவிட்டுள்ளன.

  • தரவுக் கிடங்கு என்பது நிறுவனத்தின் செயல்பாட்டுத் தரவுத்தளங்களிலிருந்து தனியாகப் பராமரிக்கப்படும் தரவுத்தளம்.
  • அது பல்வேறு பயன்பாட்டு முறைமைகளை ஒருங்கிணைக்க உதவுகிறது.
இன்மனின் வரையறை — சொல் மாறாமல் கற்கவும்

William H. Inmon கூறுவதன்படி: "தரவுக் கிடங்கு என்பது முகாமைத்துவத்தின் முடிவெடுக்கும் செயல்முறையை ஆதரிக்கும் பொருள் நோக்கிய, ஒருங்கிணைக்கப்பட்ட, காலத்துடன் மாறுபடும், நிலையழியாத தரவுகளின் தொகுப்பு."

தொடர்புநிலைத் தரவுத்தளங்கள், பரிவர்த்தனைச் செயலாக்க முறைமைகள், கோப்பு முறைமைகளிலிருந்து தரவுக் கிடங்கை வேறுபடுத்துபவை இந்த நான்கு முக்கிய சொற்கள்:

முக்கிய சொல் பொருள் எடுத்துக்காட்டு
பொருள் நோக்கியது முக்கிய பொருள்களைச் (வாடிக்கையாளர், வழங்குநர், தயாரிப்பு, விற்பனை) சுற்றி ஒழுங்கமைக்கப்பட்டது. அன்றாடச் செயல்பாடுகளுக்குப் பதிலாக முடிவெடுப்போருக்கான மாதிரியாக்கத்திலும் பகுப்பாய்விலும் கவனம் செலுத்துகிறது "விலைப்பட்டியல் உள்ளீடு" பயன்பாட்டுக்குப் பதிலாக "விற்பனை" பொருட்பகுதி
ஒருங்கிணைக்கப்பட்டது பல பல்வகை மூலங்களிலிருந்து (தொடர்புநிலைத் தரவுத்தளங்கள், தட்டைக் கோப்புகள், நிகழ்நிலைப் பரிவர்த்தனைப் பதிவுகள்) உருவாக்கப்பட்டது. தூய்மைப்படுத்தலும் ஒருங்கிணைப்பும், பெயரிடல், குறியாக்கம், பண்புக்கூறு அளவைகள் சீராக இருப்பதை உறுதிப்படுத்துகின்றன ஒரு மூலத்தில் M/F, மற்றொன்றில் 1/0 என்றில்லாமல் எல்லா இடங்களிலும் பாலினம் M/F எனச் சேமிக்கப்படுகிறது
காலத்துடன் மாறுபடுவது வரலாற்றுப் பார்வையில் தரவைச் சேமிக்கிறது (கடந்த 5–10 ஆண்டுகள்). ஒவ்வொரு சாவிக் கட்டமைப்பிலும் காலக் கூறு மறைமுகமாகவோ வெளிப்படையாகவோ உள்ளது கடந்த 8 ஆண்டுகளின் மாதவாரி விற்பனை
நிலையழியாதது வழக்கமான செயல்பாட்டுப் பரிவர்த்தனைகளுக்குப் பதிலாக கட்டுப்படுத்தப்பட்ட ஏற்றங்களாலும் புதுப்பிப்புகளாலும் பராமரிக்கப்படும் நிலையான பகுப்பாய்வுத் தரவு. காப்புப்பிரதி, மீட்பு, பாதுகாப்பான ஒரேநேர வாசிப்பு/ஏற்றங்கள் இன்னும் தேவைப்படலாம் இரவு ஏற்றம்; பின்னர் வாசிப்புக்கு மட்டுமான வினவல்கள்
நினைவுக்குறிப்பு: "SITN"

Subject — பொருள் · Integrated — ஒருங்கிணைப்பு · Time-variant — காலமாற்றம் · Nonvolatile — நிலையழியாமை. "Sales In Time, Never changed" — காலத்திலுள்ள விற்பனை, ஒருபோதும் மாற்றப்படாதது — எனச் சொல்லவும்.

3OLTP vs OLAP

OLTP மற்றும் OLAP

கடையில் ஒரு விற்பனையைப் பதிவு செய்வது OLTP. கடந்த மூன்று ஆண்டுகளின் மாவட்டவாரி விற்பனையை ஒப்பிடுவது OLAP. ஒன்றில் வேகமான transactions; மற்றொன்றில் பெரிய summary queries முக்கியம்.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

OLTP: clerk/application பயன்பாடு; short transactions; current detailed data; பல concurrent users. OLAP: analyst; complex read/aggregation; historical data; decision support. OLTP-இல் transaction throughput முக்கியம்; OLAP-இல் complex query response time முக்கியம். இரண்டிற்கும் schema, indexing, workload requirements வேறு.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

OLTP vs OLAP ஆறு contrasts: clerk/analyst; daily operations/decision support; current detailed/historical integrated; short record updates/complex grouped queries; read-write/mostly analytical reads; transaction throughput/query latency. User counts/GB/TB பாடத்தின் illustrative sizes; தற்போதைய எல்லா systems-க்கும் fixed limit அல்ல. Operational DB-லும் history இருக்கலாம்; warehouse-லும் detailed facts இருக்கலாம்.

OLTP (operational DB) OLAP (data warehouse)
Users Clerk, IT professional Knowledge worker (analysts, managers)
Function Day-to-day operations Decision support
DB design Application-oriented Subject-oriented
Data Current, up-to-date, detailed, flat relational, isolated Historical, summarised, multidimensional, integrated, consolidated
Usage Repetitive Ad-hoc
Access Read/write, index/hash on primary key Lots of scans (mostly read)
Unit of work Short, simple transaction Complex query
Records accessed Tens Millions
Number of users Thousands Hundreds
DB size 100 MB – GB 100 GB – TB
Metric Transaction throughput Query throughput, response time
  • OLTP systems handle online transaction and query processing: purchasing, inventory, manufacturing, banking, payroll, registration, accounting.
  • OLAP systems serve knowledge workers doing data analysis and decision making, presenting data in various formats for diverse users.
Exam focus

"Compare OLTP and OLAP" is very likely. Draw this table with at least 6 rows. Users, function, data, access, unit of work and metric are the most important.

OLTP (செயல்பாட்டுத் தரவுத்தளம்) OLAP (தரவுக் கிடங்கு)

செயல்பாடு அன்றாடச் செயல்பாடுகள் முடிவெடுத்தல் ஆதரவு
தரவுத்தள வடிவமைப்பு பயன்பாடு நோக்கியது பொருள் நோக்கியது
தரவு தற்போதையது, புதுப்பிக்கப்பட்டது, விரிவானது, தட்டையான தொடர்புநிலை, தனிமைப்படுத்தப்பட்டது வரலாற்று, சுருக்கப்பட்ட, பல்பரிமாண, ஒருங்கிணைக்கப்பட்ட, ஒருங்குதிரட்டப்பட்ட
பயன்பாடு மீண்டும் மீண்டும் நிகழ்வது தேவைக்கேற்ப

பயனர் எண்ணிக்கை ஆயிரங்கள் நூறுகள்
தரவுத்தள அளவு 100 MB – GB 100 GB – TB
அளவீடு பரிவர்த்தனைச் செயல்வீதம் வினவல் செயல்வீதம், பதில் நேரம்
  • OLTP முறைமைகள் நிகழ்நிலைப் பரிவர்த்தனை மற்றும் வினவல் செயலாக்கத்தைக் கையாள்கின்றன: கொள்வனவு, இருப்பு, உற்பத்தி, வங்கி, சம்பளம், பதிவு, கணக்கியல்.
  • OLAP முறைமைகள் தரவுப் பகுப்பாய்வும் முடிவெடுத்தலும் செய்யும் அறிவுப் பணியாளர்களுக்குச் சேவை செய்து, பல்வேறு பயனர்களுக்குத் தரவைப் பல வடிவங்களில் வழங்குகின்றன.
Exam focus

"OLTP, OLAP ஆகியவற்றை ஒப்பிடுக" என்பது மிகவும் சாத்தியமான கேள்வி. குறைந்தது 6 வரிசைகளுடன் இந்த அட்டவணையை வரையவும். பயனர்கள், செயல்பாடு, தரவு, அணுகல், வேலை அலகு, அளவீடு ஆகியவை மிகவும் முக்கியம்.

4Why keep the warehouse separate?

Warehouse-ஐ ஏன் தனியாக வைப்பது?

பெரிய analysis query ஓடும்போது cashier-இன் விற்பனை பதிவு மெதுவாகக் கூடாது. மேலும் historical data, ஒரே வடிவிலான தகவல் தேவை. அதனால் operational system-இலிருந்து analysis system-ஐப் பிரிப்போம்.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

பிரிப்பதற்கான மூன்று காரணங்கள்: analytical scans operational response-ஐ slow செய்யலாம்; transaction workload/locking மற்றும் long analysis வேறு tuning தேவை; historical integrated/consolidated data analysis-க்கு தேவை. இதனால் workload isolation உதவும். Physical separation ஒரு common architecture; எல்லா designs-க்கும் கட்டாயம் அல்ல; mixed workloads-ஐ ஆதரிக்கும் systems-உம் உள்ளன.

Why not just run analysis queries on the operational database? Three reasons:

1. Performance of both systems - The operational DB is tuned for known tasks: indexing and hashing on primary keys, finding particular records. - Warehouse queries are complex. They compute large groups at summarised levels and need multidimensional organisation. - Running OLAP queries on the operational DB would substantially degrade operational performance.

2. Concurrency control and recovery - The operational DB processes many concurrent transactions and needs locking and logging. - OLAP queries are mainly reads, while ETL/refresh changes stored data; consistent reads and safe refresh/recovery still matter. - Long analytical queries can compete with short operational transactions for resources. Separating/tuning workloads can protect throughput; this does not mean warehouse recovery or concurrency safeguards should be removed.

3. Different data - Decision support needs historical data, which operational DBs usually don't keep. - Operational DBs hold detailed raw data that must be consolidated (aggregated, summarised) before analysis. - Data from different sources must be integrated.

Trend

Operational RDBMS vendors are starting to optimise their systems for OLAP queries, so the separation between OLTP and OLAP is expected to decrease.

செயல்பாட்டுத் தரவுத்தளத்திலேயே பகுப்பாய்வு வினவல்களை ஏன் இயக்கக்கூடாது? மூன்று காரணங்கள்:

1. இரு முறைமைகளின் செயல்திறன் - செயல்பாட்டுத் தரவுத்தளம் அறியப்பட்ட பணிகளுக்காகச் சீரமைக்கப்பட்டது: முதன்மைச் சாவிகளில் சுட்டியிடலும் ஹாஷிங்கும், குறிப்பிட்ட பதிவுகளைக் கண்டறிதலும். - கிடங்கு வினவல்கள் சிக்கலானவை. அவை சுருக்கப்பட்ட நிலைகளில் பெரிய குழுக்களைக் கணக்கிட்டு, பல்பரிமாண ஒழுங்கமைப்பைத் தேவைப்படுத்துகின்றன. - செயல்பாட்டுத் தரவுத்தளத்தில் OLAP வினவல்களை இயக்குவது செயல்பாட்டுச் செயல்திறனைப் பெரிதும் குறைக்கும்.

2. ஒரேநேரக் கட்டுப்பாடும் மீட்பும் - செயல்பாட்டுத் தரவுத்தளம் பல ஒரேநேரப் பரிவர்த்தனைகளைச் செயலாக்குகிறது; பூட்டுதலும் பதிவேடும் தேவை. - OLAP வினவல்கள் பெரும்பாலும் வாசிப்புகள்; ETL/புதுப்பித்தல் சேமித்த தரவை மாற்றுகிறது; சீரான வாசிப்புகளும் பாதுகாப்பான புதுப்பித்தல்/மீட்பும் இன்னும் முக்கியம். - நீண்ட பகுப்பாய்வு வினவல்கள் வளங்களுக்காகக் குறுகிய செயல்பாட்டுப் பரிவர்த்தனைகளுடன் போட்டியிடலாம். பணிச்சுமைகளைப் பிரிப்பது/சீரமைப்பது செயல்வீதத்தைப் பாதுகாக்கலாம்; கிடங்கின் மீட்பு அல்லது ஒரேநேரப் பாதுகாப்புகளை நீக்க வேண்டும் என்பது இதன் பொருளல்ல.

3. வெவ்வேறு தரவு - முடிவெடுத்தல் ஆதரவுக்கு வரலாற்றுத் தரவு தேவை; செயல்பாட்டுத் தரவுத்தளங்கள் பொதுவாக அதை வைத்திருப்பதில்லை. - செயல்பாட்டுத் தரவுத்தளங்களிலுள்ள விரிவான மூலத் தரவு, பகுப்பாய்வுக்கு முன் ஒருங்குதிரட்டப்பட (திரட்டப்பட, சுருக்கப்பட) வேண்டும். - வெவ்வேறு மூலங்களின் தரவு ஒருங்கிணைக்கப்பட வேண்டும்.

போக்கு

செயல்பாட்டு RDBMS வழங்குநர்கள் OLAP வினவல்களுக்காகத் தமது முறைமைகளை உகப்பாக்கத் தொடங்கியுள்ளதால், OLTP–OLAP பிரிவு குறையும் என எதிர்பார்க்கப்படுகிறது.

5The multidimensional data model

பல பரிமாணப் பார்வை

விற்பனையை product, place, time என்ற பல Dimensions வழியாகப் பார்க்கலாம். Amount என்பது Measure. ஒரே தகவலில் roll-up, drill-down, slice, dice செய்து வெவ்வேறு கேள்விகளுக்குப் பதில் பெறலாம்.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

Dimension ஒப்பிடும் திசை — time, place, product; Measure கணக்கிடும் மதிப்பு — sales amount. Cube என்பது கட்டாயம் மூன்று dimensions மட்டும் அல்ல. ஒரே product/location-க்கு months கூட்டினால் time roll-up. Grand total-ஐ அனைத்து cells-உடன் மீண்டும் கூட்டி double counting செய்யக்கூடாது.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Dimensions எந்த perspectives? time,item,branch,location. Facts/measures எதை அளக்கிறோம்? dollars_sold,units_sold. Fact table keys மூலம் dimension descriptions-உடன் இணையும். 2-D time×item; location சேர்த்தால்3-D; supplier சேர்த்தால்4-D. Cube என்பது logical n-dimensional view; disk-இல் அவசியம் geometric cube அல்ல. Measures-ஐ aggregate செய்யும் விதி அதன் பொருளுக்குப் பொருந்தவேண்டும்.

Data warehouses and OLAP tools use a multidimensional data model, which views data as a data cube. A cube is defined by dimensions and facts.

Dimensions

The perspectives or entities the organisation wants to keep records about.

Sales example: time, item, branch, location.

Each dimension can have a dimension table describing it. For example, item has item_name, brand and type.

Facts

Numerical measures: the quantities we analyse across dimensions.

Sales example: dollars_sold, units_sold, amount_budgeted.

The fact table holds the measures plus keys to each dimension table. The model is organised around a subject (e.g. sales) represented by the fact table.

பரிமாணங்கள்

நிறுவனம் பதிவுகளை வைத்திருக்க விரும்பும் பார்வைகள் அல்லது உருப்பொருட்கள்.

விற்பனை எடுத்துக்காட்டு: காலம், பொருள், கிளை, இடம்.

ஒவ்வொரு பரிமாணத்தையும் விவரிக்கும் பரிமாண அட்டவணை இருக்கலாம். எ.கா. பொருளுக்கு item_name, brand, type உள்ளன.

உண்மைகள்

எண் அளவைகள்: பரிமாணங்களுக்கிடையே நாம் பகுப்பாய்வு செய்யும் அளவுகள்.

விற்பனை எடுத்துக்காட்டு: dollars_sold, units_sold, amount_budgeted.

6Lattice of cuboids

Cuboid-களின் தொடர்பு

எல்லா dimensions-உம் உள்ள விரிவான cuboid-இலிருந்து சில dimensions-இல் மட்டும் totals எடுக்கலாம். அவற்றின் தொகுப்பு Lattice. மேலே செல்லச் செல்ல சுருக்கம் அதிகம்; கீழே நுணுக்கம் அதிகம்.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

n dimensions ஒவ்வொன்றிலும் base/all தேர்வு என்ற எளிய நிலையில் 2ⁿ cuboids. Base cuboid மிக விரிவானது; apex all-dimensions aggregated; நடுவில் பல summaries. Roll-up மேலும் சுருக்கம்; drill-down நுணுக்கம்; slice ஒரு dimension-க்கு ஒரு value; dice பல dimensions-இல் ranges/subsets. Pivot காட்சியின் திசையை மாற்றும்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

n dimensions, hierarchies இல்லாமல் 2ⁿ cuboids;4 dimensions→1+4+6+4+1=16. Base அனைத்து dimensions/detail; apex all=0-D summary. Roll-up city→country/remove dimension; drill-down reverse; slice time=Q1; dice பல dimension constraints. Hierarchy levels இருந்தால் count formula வேறு; 2ⁿ-ஐ அங்கே நேரடியாகப் பயன்படுத்தாதீர்கள்.

Given a set of dimensions, we can make a cuboid for every possible subset of them. Each cuboid is a different level of summarisation. Together they form the lattice of cuboids, which is called a data cube.

n dimensions (no hierarchies) → 2n cuboids e.g. 4 dimensions → 24 = 16 cuboids
Term Meaning 4-D example
Base cuboid Lowest level of summarisation: all n dimensions {time, item, location, supplier}
Apex cuboid Highest summarisation: 0-D, everything summed into one value, written all Total dollars_sold over everything
Non-base cuboid Anything in between {time, item, location}: 3-D, summarised over all suppliers

The lesson introduction names the OLAP operations used on cubes:

Operation Effect
Roll-up Summarise: climb a concept hierarchy (city → country) or remove a dimension. In the explorer above, unticking a dimension is a roll-up.
Drill-down Reverse of roll-up: go to more detail (quarter → month) or add a dimension
Slice Select on one dimension, e.g. time = Q1, giving a sub-cube
Dice Select on two or more dimensions, e.g. time ∈ {Q1, Q2} and location ∈ {Toronto, Vancouver}

கொடுக்கப்பட்ட பரிமாணத் தொகுப்பின் சாத்தியமான ஒவ்வொரு உட்கணத்துக்கும் கனச்செவ்வகத்தை உருவாக்கலாம். ஒவ்வொன்றும் வெவ்வேறு சுருக்க நிலை. அவை இணைந்து கனச்செவ்வகங்களின் பின்னலை உருவாக்குகின்றன; அது தரவுக் கனசதுரம் எனப்படுகிறது.

n பரிமாணங்கள் (படிநிலைகளின்றி) → 2n கனச்செவ்வகங்கள் எ.கா. 4 பரிமாணங்கள் → 24 = 16 கனச்செவ்வகங்கள்
சொல் பொருள் 4-D எடுத்துக்காட்டு
அடிப்படைக் கனச்செவ்வகம் மிகக்குறைந்த சுருக்க நிலை: அனைத்து n பரிமாணங்களும் {காலம், பொருள், இடம், வழங்குநர்}
உச்சிக் கனச்செவ்வகம் மிக உயர்ந்த சுருக்கம்: 0-D, அனைத்தும் ஒரு பெறுமதியாகக் கூட்டப்பட்டு all என எழுதப்படுகிறது அனைத்திலும் விற்ற மொத்த டொலர்கள்
அடிப்படையல்லாத கனச்செவ்வகம் இடைப்பட்ட எதுவும் {காலம், பொருள், இடம்}: 3-D, அனைத்து வழங்குநர்களையும் சுருக்கியது

கனச்செவ்வகங்களை எண்ணவும்

பரிமாணங்கள் {காலம், பொருள், இடம், வழங்குநர்}:

  • 0-D: 1 (உச்சி)
  • 1-D: 4
  • 2-D: 6
  • 3-D: 4
  • 4-D: 1 (அடிப்படை)

மொத்தம் = 1 + 4 + 6 + 4 + 1 = 16 = 24

OLAP செயல்பாடுகள் (முன்னோட்டம்)

கனசதுரங்களில் பயன்படுத்தப்படும் OLAP செயல்பாடுகளைப் பாட அறிமுகம் பெயரிடுகிறது:

செயல்பாடு விளைவு
மேல்சுருக்கம் (Roll-up) சுருக்குதல்: கருத்துப் படிநிலையில் மேலே செல்லுதல் (நகரம் → நாடு) அல்லது பரிமாணத்தை நீக்குதல். மேலுள்ள ஆராய்வுக் கருவியில் பரிமாணத்தின் தெரிவை நீக்குவது மேல்சுருக்கம்.
கீழ்விரிப்பு (Drill-down) மேல்சுருக்கத்தின் எதிர்: மேலும் விவரத்துக்குச் செல்லுதல் (காலாண்டு → மாதம்) அல்லது பரிமாணம் சேர்த்தல்
துண்டாக்கல் (Slice) ஒரு பரிமாணத்தில் தேர்வுசெய்தல்; எ.கா. காலம் = Q1; துணைக் கனசதுரம் கிடைக்கும்
பல்துண்டாக்கல் (Dice) இரண்டு அல்லது அதிகமான பரிமாணங்களில் தேர்வுசெய்தல்; எ.கா. காலம் ∈ {Q1, Q2}, இடம் ∈ {Toronto, Vancouver}

8Quick revision sheet

விரைவாக நினைவுபடுத்திக்கொள்ள

பழைய தரவும் ஏன் தேவை?

இன்றைய விற்பனைப் பதிவு மட்டும் நீண்டகால வளர்ச்சியைக் காட்டாது. பல ஆண்டுகள், பல பிரிவுகளின் தகவலைச் சேர்த்து ஒப்பிட்டால் முடிவு எடுக்க உதவும். இதற்கான தனிச் சேமிப்புதான் Warehouse.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Data warehouse பல sources-ஐ clean/integrate/transform செய்து historical analysis-க்கு ஒரே consistent view தருகிறது. OLAP மூலம் detail/summarised levels-இல் interactive queries; mining மூலம் associations/classifiers/clusters. Warehouse அமைப்பதே preprocessing-க்கு உதவும்; warehouse வைத்திருப்பதால் data தானாக accurate அல்லது useful ஆகிவிடாது.

Data warehouse எளிமையாக

பல மூலங்களிலிருந்து ஒருங்கிணைக்கப்பட்ட வரலாற்றுத் தகவலை ஆய்விற்காக வைத்திருப்பது Data warehouse. Subject-oriented, integrated, time-variant, non-volatile அதன் முக்கிய பண்புகள். நாளாந்தப் பதிவைத் திருத்தும் அமைப்பல்ல.

Warehouse-இன் நான்கு பண்புகள்: subject-oriented — customer/sales போன்ற பொருளை மையமாக்குதல்; integrated — sources ஒரே codes/units; time-variant — historical periods; nonvolatile — analysis data பொதுவாக stable, transaction-style update அல்ல. Nonvolatile என்றால் warehouse ஒருபோதும் load/update ஆகாது என்று அர்த்தமில்லை. ETL மூலம் புதிய snapshots அல்லது records சேர்க்கப்படலாம்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

SITN: subject-oriented=customer/sales போன்ற analysis subject; integrated=ஒரே codes/units/meaning; time-variant=historical perspective; nonvolatile=day-to-day transaction போல தொடர்ந்து overwrite செய்யாமல் controlled load/refresh மற்றும் analysis. Nonvolatile என்றால் backup, recovery, concurrency தேவையில்லை என்பதல்ல. “5–10 years” course example; எல்லா warehouses-க்கும் fixed retention இல்லை.

OLTP மற்றும் OLAP

கடையில் ஒரு விற்பனையைப் பதிவு செய்வது OLTP. கடந்த மூன்று ஆண்டுகளின் மாவட்டவாரி விற்பனையை ஒப்பிடுவது OLAP. ஒன்றில் வேகமான transactions; மற்றொன்றில் பெரிய summary queries முக்கியம்.

OLTP: clerk/application பயன்பாடு; short transactions; current detailed data; பல concurrent users. OLAP: analyst; complex read/aggregation; historical data; decision support. OLTP-இல் transaction throughput முக்கியம்; OLAP-இல் complex query response time முக்கியம். இரண்டிற்கும் schema, indexing, workload requirements வேறு.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

OLTP vs OLAP ஆறு contrasts: clerk/analyst; daily operations/decision support; current detailed/historical integrated; short record updates/complex grouped queries; read-write/mostly analytical reads; transaction throughput/query latency. User counts/GB/TB பாடத்தின் illustrative sizes; தற்போதைய எல்லா systems-க்கும் fixed limit அல்ல. Operational DB-லும் history இருக்கலாம்; warehouse-லும் detailed facts இருக்கலாம்.

Warehouse-ஐ ஏன் தனியாக வைப்பது?

பெரிய analysis query ஓடும்போது cashier-இன் விற்பனை பதிவு மெதுவாகக் கூடாது. மேலும் historical data, ஒரே வடிவிலான தகவல் தேவை. அதனால் operational system-இலிருந்து analysis system-ஐப் பிரிப்போம்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

பிரிப்பதற்கான மூன்று காரணங்கள்: analytical scans operational response-ஐ slow செய்யலாம்; transaction workload/locking மற்றும் long analysis வேறு tuning தேவை; historical integrated/consolidated data analysis-க்கு தேவை. இதனால் workload isolation உதவும். Physical separation ஒரு common architecture; எல்லா designs-க்கும் கட்டாயம் அல்ல; mixed workloads-ஐ ஆதரிக்கும் systems-உம் உள்ளன.

பல பரிமாணப் பார்வை

விற்பனையை product, place, time என்ற பல Dimensions வழியாகப் பார்க்கலாம். Amount என்பது Measure. ஒரே தகவலில் roll-up, drill-down, slice, dice செய்து வெவ்வேறு கேள்விகளுக்குப் பதில் பெறலாம்.

Dimension ஒப்பிடும் திசை — time, place, product; Measure கணக்கிடும் மதிப்பு — sales amount. Cube என்பது கட்டாயம் மூன்று dimensions மட்டும் அல்ல. ஒரே product/location-க்கு months கூட்டினால் time roll-up. Grand total-ஐ அனைத்து cells-உடன் மீண்டும் கூட்டி double counting செய்யக்கூடாது.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Dimensions எந்த perspectives? time,item,branch,location. Facts/measures எதை அளக்கிறோம்? dollars_sold,units_sold. Fact table keys மூலம் dimension descriptions-உடன் இணையும். 2-D time×item; location சேர்த்தால்3-D; supplier சேர்த்தால்4-D. Cube என்பது logical n-dimensional view; disk-இல் அவசியம் geometric cube அல்ல. Measures-ஐ aggregate செய்யும் விதி அதன் பொருளுக்குப் பொருந்தவேண்டும்.

Cuboid-களின் தொடர்பு

எல்லா dimensions-உம் உள்ள விரிவான cuboid-இலிருந்து சில dimensions-இல் மட்டும் totals எடுக்கலாம். அவற்றின் தொகுப்பு Lattice. மேலே செல்லச் செல்ல சுருக்கம் அதிகம்; கீழே நுணுக்கம் அதிகம்.

n dimensions ஒவ்வொன்றிலும் base/all தேர்வு என்ற எளிய நிலையில் 2ⁿ cuboids. Base cuboid மிக விரிவானது; apex all-dimensions aggregated; நடுவில் பல summaries. Roll-up மேலும் சுருக்கம்; drill-down நுணுக்கம்; slice ஒரு dimension-க்கு ஒரு value; dice பல dimensions-இல் ranges/subsets. Pivot காட்சியின் திசையை மாற்றும்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

n dimensions, hierarchies இல்லாமல் 2ⁿ cuboids;4 dimensions→1+4+6+4+1=16. Base அனைத்து dimensions/detail; apex all=0-D summary. Roll-up city→country/remove dimension; drill-down reverse; slice time=Q1; dice பல dimension constraints. Hierarchy levels இருந்தால் count formula வேறு; 2ⁿ-ஐ அங்கே நேரடியாகப் பயன்படுத்தாதீர்கள்.
