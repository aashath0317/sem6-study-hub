## Week 01 — Humans, Computers & Interactions

**தமிழ் சுருக்கம்:** HCI என்பது **மனிதர்களும் computers-உம் எப்படி ஒன்றாக வேலை செய்கிறார்கள்** என்று படிப்பது. இது பல துறைகள் சேர்ந்த ஒரு field. Interaction **இரண்டு திசையில்** நடக்கிறது: நாம் input கொடுக்கிறோம், system feedback தருகிறது. நல்ல interface **"கண்ணுக்குத் தெரியாமல்"** இருக்கும். அப்போது user task-இல் மட்டுமே கவனம் செலுத்துவார்.

| Concept | Key point |
|---|---|
| Origin | HMI → HCI, late 1970s/early 1980s; the term appeared around 1980 |
| Vannevar Bush (1945) | "As We May Think": the human at the centre, technology in the background |
| Multi-disciplinary | Computer science · cognitive psychology · ergonomics · design/arts · sociology · application domains |
| Ubiquitous computing | Processors embedded everywhere: ATMs, cars, rice cookers |
| Senses used | Sight (primary), hearing, touch. Taste and smell are experimental |
| Perception | Shaped by context and experience (the "credit" example) |
| Interaction types | **Intentional** (click Print) vs **unintentional** (a face-recognition door) |
| Task-centred | Users interact with the **task**; the interface should be invisible |
| HCI vs HFE | HCI = digital only; Human Factors Engineering = digital + physical |
| HCI space | HFE → {Industrial design, **HCI**, Product design}; HCI → {UI, UX, Interaction design} |
| Applications (3 pillars) | Technologies · Ideas · Domains |

## Week 02 — ⭐ Interaction Models, Ergonomics & Styles

**தமிழ் சுருக்கம்:** **Norman-இன் 7 stages** model, user ஒரு goal-இலிருந்து action-க்கு எப்படிப் போகிறார், பிறகு விளைவை எப்படி மதிப்பிடுகிறார் என்று காட்டுகிறது. அதில் **இரண்டு இடைவெளிகள் (gulfs)** உள்ளன:

- **Execution gulf:** "எப்படிச் செய்வது?"
- **Evaluation gulf:** "என்ன நடந்தது?"

**Norman's 7 stages:**

1. **Goal**: form the goal
2. **Intention**: form the intention
3. **Action specification**: specify the action
4. **Execution**: execute the action
5. **Perception**: perceive the system state
6. **Interpretation**: interpret the state
7. **Evaluation**: evaluate against the goal

- **Execution loop** = stages 2–4.
- **Evaluation loop** = stages 5–7.

| Gulf | Meaning | Fix |
|---|---|---|
| **Gulf of execution** | Gap between what the user **intends** and the actions the system **allows** | Affordances, signifiers, mapping, clear controls |
| **Gulf of evaluation** | Gap between the **system state** and the user's ability to **interpret** it | Clear, immediate **feedback** and visible state |

| Error | Meaning | Fix |
|---|---|---|
| **Slip** | Right goal, **wrong action** (e.g. tapping a tiny button next to the target) | **Fix the design**: bigger targets, spacing, undo, confirmation |
| **Mistake** | **Wrong goal or plan**, from a wrong mental model | **Educate the user**: better conceptual model, help, feedback |

**Abowd & Beale framework:**

- Four components: **U**ser, **I**nput, **S**ystem, **O**utput.
- Execution side: **Articulation**, Performance.
- Evaluation side: **Presentation**, Observation.

**Ergonomics:** the physical side of interaction: controls, environment, health, colour.

**Direct vs indirect manipulation:**

- **Direct:** act on the object itself, e.g. bold a selected word.
- **Indirect:** act through a separate medium, e.g. paint a real wall via a simulator.

**Interaction styles:**

- Command line
- Menus
- Natural language
- Q&A / query
- Forms
- WIMP
- 3D
- Kinetic / haptic

:::exam
**⭐ Q2(a) frame: explain the execution/evaluation loop with an example [12].**

> Norman's model describes interaction in seven stages. The user forms a **goal** ("print the report"), forms an **intention** ("use the Print command"), **specifies** the action sequence (File → Print → OK) and **executes** it. This is the execution loop. The user then **perceives** the system state (printer icon, sound), **interprets** it ("it is printing") and **evaluates** whether the goal was met (the pages came out). This is the evaluation loop. If the goal is not met, the cycle repeats with a new intention.
:::

## Week 03 — The Human as an Information Processor

**தமிழ் சுருக்கம்:** மனிதனை ஒரு computer போல யோசிக்கலாம்:

- **Perceptual:** input, அதாவது புலன்கள்.
- **Cognitive:** processing, அதாவது நினைவு, கவனம்.
- **Motor:** output, அதாவது கை அசைவு.

Short-term memory **சிறியது**. அதனால் தகவல்களை **chunks**-ஆகப் பிரித்துக் கொடுக்க வேண்டும்.

| Topic | Key point |
|---|---|
| 3 sub-systems | Perceptual (input) → Cognitive (processing) → Motor (output) |
| Vision | Directional. Centre of the screen = critical items; top-right = alerts. About 1 in 12 men are colour-blind |
| Hearing | Non-directional. Good for alerts, but can annoy |
| Touch | Personal and private: vibration, key feel |
| Sensory memory | Iconic (sight), echoic (hearing), haptic (touch). Very short; attention moves items to working memory |
| Short-term memory | Limited capacity (classic 7 ± 2 chunks); chunking helps |
| Long-term memory | **Episodic** (events) vs **semantic** (a network of facts) |
| Chunking | Groups of 3–4 items, e.g. phone numbers 077 123 4567 |
| Cognitive load | Too much demand causes errors; too little causes boredom |
| Being watched | Anxiety uses up working memory, so performance drops |
| Attention | **Selective** (focus on one thing; works better) vs **divided** (switching has a cost) |
| Motor | Target size and spacing matter; see Fitts's law (Week 09) |

## Week 04 — Designing for Users: Tasks, Contexts & Perspectives

**தமிழ் சுருக்கம்:** Interface-ஐ அல்ல, **task-ஐ** முதலில் புரிந்துகொள்ளுங்கள். ஒரு design வெற்றி பெற மூன்றும் வேண்டும்: **useful** (பயனுள்ளது), **usable** (பயன்படுத்த எளிது), **used** (மக்கள் உண்மையில் பயன்படுத்துகிறார்கள்). User-ஐ மூன்று கோணங்களில் பார்க்கலாம்.

**3 contexts of "use":**

| | Meaning |
|---|---|
| **Useful** | Lets the user achieve the task |
| **Usable** | Effective, efficient, pleasurable, with no fear of failure |
| **Used** | Repeated long-term use, i.e. real acceptance |

**3 user perspectives:**

| Perspective | Focus | Method | Weakness |
|---|---|---|---|
| **Processor** | Human limits; quantitative | Measure times and errors | Can't explain **why**; no redesign help |
| **Predictor** | Human knowledge; qualitative | Ex-situ: think-aloud, cognitive walkthrough | Ignores real context |
| **Participant** | Context of use | In-situ field study | Authentic but **expensive** |

**GPS turn example:**

- Processor view: prompt **2 s** before the turn.
- Predictor view: prompt **10 s** before.
- Participant view: prompt at **500 m**, with multiple alerts.
- Lesson: the algorithm-optimal route is not always driver-friendly.

**UX goes beyond interaction:** it includes emotion and personal fit, at the level of the individual, the team and society.

## Week 05 — Feedback Cycles & Levels of Design

**தமிழ் சுருக்கம்:** ஒவ்வொரு action-க்கும் ஒரு **effect** உண்டு. அந்த effect பற்றிய தகவல் user-க்குத் திரும்பி வருவதுதான் **feedback**. உதாரணம்: volume button அழுத்தினால் சத்தம் கூடுகிறது, அது effect. அதை நீங்கள் கேட்கிறீர்கள், அது feedback. Norman design-ஐ **மூன்று நிலைகளாகப்** பிரிக்கிறார்.

**Feedback cycles:**

- **Interaction:** the effect of an action between 2+ objects.
- **Feedback:** information about that effect, returned to the actor.
- **Examples:** kettle whistle, bank "success/failed" message, ATM.
- We learn through feedback cycles, so each next interaction improves.

**The two bridges:**

| Bridge | Steps |
|---|---|
| **Execution** | Plan → Specify → Perform |
| **Evaluation** | Perceive → Interpret → Compare |

**The 7 questions:**

- **User's version:**
    1. What do I want?
    2. What are the alternatives?
    3. What can I do?
    4. How do I do it?
    5. What happened?
    6. What does it mean?
    7. Is it okay?
- **Designer's version:** how easily can the user determine the function, tell what actions are possible, map intention to action, perform it, perceive the state, interpret it, and evaluate it?

**Norman's 3 levels of design:**

| Level | About | Example |
|---|---|---|
| **Visceral** | Look and feel: the instant reaction | A beautiful phone |
| **Behavioural** | Usability: how it works in use | Easy, fast controls |
| **Reflective** | Meaning, pride, brand, self-image | "Owning this says something about me" |

## Week 06 — Direct Manipulation & Invisible Interfaces

**தமிழ் சுருக்கம்:** **Direct manipulation** என்றால் பொருளையே நேரடியாகத் தொடுவது: pinch, drag. இது இரண்டு gulfs-ஐயும் குறைக்கிறது. நல்ல interface **metaphorically invisible** ஆக இருக்கும், அதாவது user அதைப் பற்றி யோசிக்கவே வேண்டியதில்லை. ஆனால் அது **literally invisible** ஆகக்கூடாது, அதாவது feedback இல்லாமல் போகக்கூடாது.

| Concept | Key point |
|---|---|
| Direct manipulation | Act on the object itself (pinch to zoom, drag a file). Narrows **both gulfs** |
| Desktop metaphor vs CLI | Drag a file into a folder vs typing `mv` syntax |
| Good design | **Metaphorically invisible, literally present** (still gives feedback) |
| Bad design | **Literally invisible**: no feedback, so the feedback cycle breaks |
| Where DM is still lacking | Fixing typos, picking emoji, car climate controls |
| Invisible **by learning** | Fades with practice (TV remote, games). **The user** does the work |
| Invisible **by design** | Invisible from the first use (a child using YouTube on an iPad). **The designer** does the work |
| Novice vs expert | Novices need ease of use; experts need efficiency |

**5 tips for invisible interfaces:**

1. Use affordances.
2. Know your user.
3. Differentiate your users.
4. Let the interface teach.
5. Talk to your users.

## Week 07 — Design Principles, Guidelines & Standards

**தமிழ் சுருக்கம்:** மூன்றுக்கும் உள்ள வேறுபாடு:

- **Principles:** பொதுவானவை, கட்டாயம் இல்லை. உதா: "feedback கொடு".
- **Guidelines:** ஆலோசனை. உதா: Apple HIG.
- **Standards:** குறிப்பானவை, **கட்டாயம்**. உதா: ISO, WCAG.

Nielsen-இன் 10, Shneiderman-இன் 8 lists exam-இல் அடிக்கடி வருகின்றன.

| | Generality | Authority | Example |
|---|---|---|---|
| **Principles** | High | Low | "Provide feedback" |
| **Guidelines** | Moderate | Advisory | Apple HIG, Material Design |
| **Standards** | Low | High, binding | ISO 9241, WCAG 2.1 |

**Norman's principles:**

- Discoverability
- Feedback
- Affordances
- Signifiers
- Mappings
- Constraints
- Conceptual models

**Nielsen's 10 heuristics:**

1. Visibility of system status
2. Match between system and the real world
3. User control and freedom
4. Consistency and standards
5. Error prevention
6. Recognition rather than recall
7. Flexibility and efficiency of use
8. Aesthetic and minimalist design
9. Help users recognise, diagnose and recover from errors
10. Help and documentation

**Shneiderman's 8 golden rules:**

1. Strive for consistency
2. Enable shortcuts
3. Offer informative feedback
4. Design dialogs to yield closure
5. Offer simple error handling
6. Permit easy reversal of actions
7. Support an internal locus of control
8. Reduce short-term memory load

**Common core of all three lists:** visibility, feedback, consistency, error prevention, memory load.

**15 universal principles:**

- Discoverability, Feedback, Constraints, Mapping, Consistency
- Affordance, Structure, Simplicity, Tolerance, Equity
- Flexibility, Perceptibility, Ease, Comfort, Documentation

**Defensive design:**

- Offer undo.
- Use non-destructive paths.
- Confirm irreversible actions.
- Never rely on **colour alone** (multi-modal).

## Week 08 — Mental Models, Representations & Error Taxonomy

**தமிழ் சுருக்கம்:** **Mental model** என்பது "இந்த system எப்படி வேலை செய்யும்" என்று user மனதுக்குள் வைத்திருக்கும் ஒரு simulation. Interface (representation), **user-இன் model-உடன்** பொருந்த வேண்டும். Programmer-இன் implementation-உடன் அல்ல. Slips, mistakes இரண்டுக்கும் மேலும் உட்பிரிவுகள் உள்ளன.

| Concept | Key point |
|---|---|
| Mental model | Internal simulation used to **predict** system behaviour |
| Bus bell example | Correct model + broken mechanism, vs changed system with no signifiers |
| Representation | The UI layer, matched to the **user's** model, not the implementation model |
| Attachment example | Old "Update" step lost files; Gmail's inline attach matches the model |

**4 traits of good representations:**

1. Make relationships explicit.
2. Bring objects and actions together.
3. Exclude extraneous detail.
4. Expose natural constraints.

**Full error taxonomy:**

| Type | Sub-type | Meaning |
|---|---|---|
| **Slip** | Action-based | Wrong action, or the right action on the wrong object |
| | Memory-lapse | Forgot one step (e.g. left the card in the ATM) |
| **Mistake** | Rule-based | Correct assessment, wrong rule applied |
| | Knowledge-based | Wrong assessment; lacks knowledge |
| | Memory-lapse | Forgot the whole goal or cycle |

**Two designer traps:**

- **Learned helplessness:** after repeated failure the user gives up. Fix: be forgiving and support different learners.
- **Expert blindness:** the designer misses "obvious" steps. Fix: test with novices.

:::exam
**⭐ Q2(c) frame: slips vs mistakes, and how to reduce them [7].**

> A **slip** occurs when the user has the right goal but performs the wrong action, for example tapping "Delete" instead of the adjacent "Save" button. Slips are reduced through design: larger, well-spaced targets, constraints, confirmation for destructive actions and undo. A **mistake** occurs when the user forms the wrong goal or plan because of an incorrect mental model, for example saving a file to the wrong place believing it is shared. Mistakes are reduced by improving the conceptual model: clear feedback, consistent design, good representations, help and training.
:::

## Week 09 — ⭐ Cognitive Modelling: GOMS, KLM & Fitts's Law

**தமிழ் சுருக்கம்:** Users இல்லாமலே, ஒரு UI-இல் ஒரு வேலைக்கு **எவ்வளவு நேரம் ஆகும்** என்று கணிக்கும் models இவை. GOMS தான் குடை (umbrella). அதன் கீழ்நிலை KLM. Pointing-க்கு Fitts's law. இவை **expert, பிழையில்லாத** user-ஐ மட்டுமே கணிக்கின்றன.

**GOMS:**

- **G**oals: what the user wants
- **O**perators: basic actions
- **M**ethods: sequences of operators
- **S**election rules: which method to choose

**KLM:** T = K + P + H + D + M + R. It models an expert, error-free user.

| Operator | Meaning | Time |
|---|---|---|
| K | Keystroke | 0.2 s |
| P | Point with the mouse | 1.1 s |
| H | Home hands (keyboard ↔ mouse) | 0.4 s |
| M | Mental preparation | 1.35 s |
| D, R | Draw, system response | Depends on the task |

M rule: put an M before a P that selects a command.

**Fitts's law:** MT = a + b·log₂(2D/W)

- **D** = distance to the target. **W** = target width.
- Far + small targets are **slow**. Big + near targets are **fast**.
- Screen edges help, because the pointer stops there, so there is less overshoot.

**Limits of predictive models:**

- No novices.
- No errors.
- No emotion or fatigue.
- Only structured goals.

**⭐ Goals vs tasks (Q3a):**

- A **goal** is the end state, the *what*: "the report is in the Projects folder".
- A **task** is the structured set of actions to reach it, the *how*: "open Explorer, select, cut, paste".
- Goals are stable. Tasks depend on the **technology**: the same goal can be done by drag-and-drop or by a command line.

## Week 10 — ⭐ Cognitive Task Analysis & HTA

**தமிழ் சுருக்கம்:**

- **CTA:** user மனதுக்குள் நடக்கும், **கண்ணுக்குத் தெரியாத** சிந்தனையை வெளிக்கொண்டு வருகிறது.
- **HTA:** ஒரு goal-ஐ **sub-tasks**-ஆகவும், அவற்றை **operations**-ஆகவும் படிப்படியாக உடைக்கிறது. ஒவ்வொரு நிலைக்கும் ஒரு **plan** எழுத வேண்டும் (வரிசை, நிபந்தனைகள்).

**HTA-ஐ ஒருமுறையாவது கையால் வரைந்து பயிற்சி செய்யுங்கள். 19 marks இதற்குத்தான்.**

**Processor- vs predictor-oriented models:**

- **Processor-oriented:** behaviourism. Observable actions (GOMS).
- **Predictor-oriented:** cognitivism. Hidden reasoning, memory, attention.

**CTA, 5 steps:**

1. Collect preliminary knowledge
2. Identify knowledge representations
3. Populate them (think-aloud)
4. Verify with users
5. Format for design

**HTA rules:**

- Goal → sub-tasks → operations, with **plans** for order and conditions.
- Write the textual version first, then draw the diagram.
- Plan example: IF email THEN 2.1, 2.2 ELSE 2.3, 2.4.
- Read it top to bottom, left to right. Finish each sub-branch first.
- **Modularity:** standard sub-tasks such as checkout and login can be reused (PayPal, Stripe).

:::exam
**⭐ Q3(b) frame: textual HTA, "move a file in Windows" [11].**

```
0. Move a file to another location
   1. Locate the file
      1.1 Open File Explorer
      1.2 Navigate to the source folder
      1.3 Find/select the file
   2. Choose a moving method
   3. Move the file
      3.1 Cut-and-paste
          3.1.1 Right-click → Cut (Ctrl+X)
          3.1.2 Navigate to destination
          3.1.3 Right-click → Paste (Ctrl+V)
      3.2 Drag-and-drop
          3.2.1 Open destination in a second window
          3.2.2 Drag the file to it
          3.2.3 Release the mouse button
   4. Handle conflicts
      4.1 If the name exists → Replace / Skip / Keep both
   5. Verify the move
      5.1 File appears in destination
      5.2 File gone from source
```

- **Plan 0:** do 1, 2, 3; then 4 if there's a conflict; then 5.
- **Plan 3:** if cut-and-paste, do 3.1; else do 3.2.

**Q3(c) diagram [8]:**

1. Draw Box 0 at the top, with boxes 1–5 in a row beneath it.
2. Under box 3, branch to 3.1 and 3.2, each with its sub-steps.
3. Write the plans beside each parent box.
4. Number every box, and underline the leaf tasks.

## Week 11 — ⭐ User-Centred Design & the Design Life Cycle

**தமிழ் சுருக்கம்:** **UCD** என்பது users-ஐ **ஆரம்பம் முதல் இறுதி வரை** design-இல் சேர்த்துக்கொள்வது. Spec-driven design users-க்கு என்ன வேண்டும் என்று **ஊகிக்கிறது**. UCD அதைக் **கண்டுபிடிக்கிறது**. Paper-இன் Q1 முழுவதும் இந்த week தான்.

**Why UCD matters (Q1a):**

- Builds systems people actually want and can use, so usability and satisfaction rise.
- Cuts errors, training and support costs.
- Catches problems **early**: fixing them late can cost up to **100×** more.
- Raises adoption and productivity.

**The 8 user characteristics (Q1b):**

| Characteristic | Design effect |
|---|---|
| Role | An admin needs different screens from a cashier |
| Age | Check real visual, motor and memory needs; don't assume |
| Gender | Investigate real needs; don't assume colour preferences |
| Education | Plain language vs technical terms |
| Culture | Colour meanings, reading direction, metaphors |
| Interests / motivation | What keeps them engaged |
| Professional level | Familiarity with domain terms |
| Computer literacy | Novices need wizards and guidance; experts want shortcuts |

Combine these into **personas**, not an "average user", and provide **dual pathways** for novices and experts.

**ISO 9241-210: the 6 UCD principles (Q1c):**

1. Based on an explicit **understanding** of users, tasks and environments
2. Users are **involved** throughout design and development
3. Driven and refined by user-centred **evaluation**
4. The process is **iterative**
5. Addresses the **whole user experience**
6. The team has **multidisciplinary** skills and perspectives

**Stakeholder levels (Q1d), with the photocopy-shop example:**

| Level | Who | Example |
|---|---|---|
| **Primary** | Use the interface directly | The shop staff operating the system |
| **Secondary** | Use its **output** but not the interface | Customers receiving copies; residents receiving SMS |
| **Tertiary** | **Affected** without any contact | Sanitation workers, neighbours |

**4-phase life cycle (Q4c):**

1. **Requirements** (needfinding)
2. **Design alternatives**
3. **Prototype**, from low fidelity (paper) to high fidelity (clickable)
4. **Evaluate**, then loop back

:::exam
**⭐ Q4(c) frame: how the life cycle produces a usable and used interface [12].**

> **Needfinding** discovers real users, tasks and context, so the design is **useful**. Generating several **design alternatives** avoids fixing on the first idea. **Prototyping**, from paper to clickable, makes ideas testable cheaply. **Evaluation** with real users exposes usability problems early. Each loop **iterates** on the findings, so effectiveness, efficiency and satisfaction improve (**usable**). Because users are involved throughout, the result fits their needs and context, so it is accepted and **used** long term.
:::

## Week 12 — ⭐ Needfinding: Biases & Methods

**தமிழ் சுருக்கம்:** Design-க்கு முன் **user-ஐயும் context-ஐயும்** புரிந்துகொள்வதுதான் needfinding. இதுவே முதல், மிக முக்கியமான stage. ஆனால் நம் **biases** நம்மை ஏமாற்றலாம். **5 biases**-ஐ நினைவில் வைக்க **COSVR** என்ற hook-ஐப் பயன்படுத்துங்கள்.

**The 7 questions to answer:**

1. Who is the user?
2. Where are they?
3. What is the context?
4. What are their goals?
5. What do they need now?
6. What are their tasks?
7. What are the subtasks?

**⭐ The 5 biases (COSVR):**

| Bias | What happens | How to avoid it |
|---|---|---|
| **C**onfirmation | Looking only for evidence that you're right | Look for where you're wrong; test empirically; ask many people |
| **O**bserver | The researcher influences the participant | Script the interaction; have the script reviewed |
| **S**ocial desirability | People give "nice" answers | Naturalistic observation; discount polite answers |
| **V**oluntary response | Only people with strong opinions reply | Broaden recruitment; examine non-response; triangulate |
| **R**ecall | People misremember past behaviour | Collect data during the activity; think-aloud |

**Needfinding methods:**

| Method | Key point |
|---|---|
| Naturalistic observation | Just watch, no talking. You can't know what they are thinking |
| Participant observation | Do the task yourself, but remember you're not the user |
| Look for hacks and errors | Workarounds (e.g. the ATM cheque) and slips/mistakes |
| Indirect observation | Diaries, interaction logs, analytics |
| Apprenticeship | Become an expert in complex tasks (ethnography) |
| Interviews | 5W + H. Unstructured, structured, semi-structured, focus group (3–10 people) |
| Think-aloud | Voice your actions; it can change behaviour, so also use retrospective |
| Surveys | Less is more · avoid bias · tie to inventory · test · iterate |

**Representing the needs:** task and subtask lists, diagrams and flowcharts. These feed the design alternatives.

## Week 13 — Evaluation: Measuring Usability

**தமிழ் சுருக்கம்:** Evaluation என்பது **usability-ஐ அளப்பது**, UCD-இன் இதயம். Evaluation method **prototype-இன் கட்டத்துக்குப்** பொருந்த வேண்டும்:

- **ஆரம்பத்தில்:** qualitative.
- **நடுவில்:** usability.
- **இறுதியில்:** quantitative.

**Evaluation through the life cycle:**

| Stage | Focus |
|---|---|
| Early | **Qualitative**: preferences, colour, readability |
| Middle | **Usability**: workload, how intuitive it is, ease of learning |
| Late | **Quantitative**: task time, jobs per day, sales |

**3 types of evaluation:**

| Type | Users? | Data |
|---|---|---|
| **Qualitative** | Yes | Preferences; no metrics |
| **Empirical** | Yes | Quantitative; **controlled experiments** (do qualitative first) |
| **Predictive** | No user session | Model-based estimates (GOMS, KLM); complement with user evidence |

**4 key terms:**

| Term | Meaning |
|---|---|
| **Reliability** | **Consistent** results over time |
| **Validity** | **Accurate** to reality. Reliable ≠ valid |
| **Generalisability** | Applies to a **broader audience** |
| **Precision** | How **specific** the measure is: 106 vs 106.4 vs 106.43 km |

Evaluate what you actually **designed**, not what you planned to design. Then **iterate**.
