1Why a different schema for warehouses?

Warehouse schema ஏன் வேறு?

Analysis-இல் பல rows-ஐச் சேர்த்து sums, comparisons செய்வோம். அதற்காக facts மற்றும் dimensions-ஐ ஒழுங்குபடுத்துகிறோம். Transaction database-இன் வடிவமே எல்லா analysis-க்கும் வேகமாக இருக்கும் என்று கருதக்கூடாது.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Warehouse analysis-க்கு fact+dimensions கொண்ட multidimensional schema எளிய group-by/join செய்ய உதவும். Star, snowflake, constellation மூன்று designs. ER என்பது operational modelling-இல் பொதுவானது; warehouse-இல் ER “பயன்படுத்தவே முடியாது” அல்ல. Data grain, relationships, query needs அடிப்படையில் schema தேர்வு செய்யப்படுகிறது.

  • Relational databases (OLTP) are designed with the entity-relationship (ER) model: a set of entities and the relationships between them.
  • A data warehouse needs a concise, subject-oriented schema that supports on-line data analysis.
  • The most popular model for a warehouse is the multidimensional model. It comes in three forms:
Star schemaSnowflake schemaFact constellation

In all three there is a fact table (holds the measures plus keys to the dimensions) and dimension tables (describe each dimension).

  • தொடர்புநிலைத் தரவுத்தளங்கள் (OLTP), உருப்பொருள்-உறவு (ER) மாதிரியால் வடிவமைக்கப்படுகின்றன: உருப்பொருட்களின் தொகுப்பும் அவற்றுக்கிடையிலான உறவுகளும்.
  • தரவுக் கிடங்குக்கு, நிகழ்நிலைத் தரவுப் பகுப்பாய்வை ஆதரிக்கும் சுருக்கமான, பொருள் நோக்கிய திட்டவடிவம் தேவை.
  • கிடங்குக்கு மிகவும் பிரபலமானது பல்பரிமாண மாதிரி. அது மூன்று வடிவங்களில் வருகிறது:
நட்சத்திரத் திட்டவடிவம்பனித்துகள் திட்டவடிவம்உண்மை விண்மீன்கூட்டம்

மூன்றிலும் உண்மை அட்டவணையும் (அளவைகளையும் பரிமாணங்களுக்கான சாவிகளையும் கொண்டது) பரிமாண அட்டவணைகளும் (ஒவ்வொரு பரிமாணத்தையும் விவரிப்பவை) உள்ளன.

2Star schema

நட்சத்திர வடிவத் தரவு அமைப்பு

நடுவில் விற்பனை போன்ற Fact table; அதைச் சுற்றி Time, Product, Customer போன்ற Dimension tables. நட்சத்திரம்போல் தோன்றுவதால் Star schema. Fact table-இல் measures மற்றும் dimension keys இருக்கும்.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

Fact table-இல் foreign keys மற்றும் numerical measures இருக்கும். Dimension table-இல் descriptive attributes. Grain “ஒரு product ஒரு shop-இல் ஒரு நாளின் sales” என்றால் ஒவ்வொரு row அதையே பிரதிநிதித்துவப்படுத்த வேண்டும். Star dimension denormalised ஆக இருப்பதால் fewer joins, எளிய queries கிடைக்கலாம்; repeated descriptions சேமிப்பை அதிகரிக்கலாம்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Star-இல் நடுவில் sales fact: time_key,item_key,branch_key,location_key + dollars_sold/units_sold. ஒவ்வொரு dimension-க்கும் ஒரே denormalised table. Location-இல் city/state/country மீண்டும் வருவதால் redundancy; joins எளிதாகலாம். Diagram-இல் keys/facts மற்றும் descriptive attributes வேறுபடுத்துங்கள்.

A central fact table connected to one table per dimension. It is the simplest schema.

  • Example (Figure 6-1): the sales fact table has keys to time, item, branch, location and two measures, dollars_sold and units_sold.
  • Each dimension is exactly one table.
Its drawback: redundancy

The location table holds (location_key, street, city, province_or_state, country). Vancouver and Victoria are both in British Columbia, Canada, so "British Columbia, Canada" is repeated in many rows:

(…, Vancouver, British Columbia, Canada) (…, Victoria, British Columbia, Canada)

ஒவ்வொரு பரிமாணத்துக்கும் ஓர் அட்டவணையுடன் இணைக்கப்பட்ட மைய உண்மை அட்டவணை. இதுவே மிக எளிய திட்டவடிவம்.

  • எடுத்துக்காட்டு (படம் 6-1): sales உண்மை அட்டவணையில் time, item, branch, location ஆகியவற்றுக்கான சாவிகளும் dollars_sold, units_sold என்ற இரு அளவைகளும் உள்ளன.
  • ஒவ்வொரு பரிமாணமும் துல்லியமாக ஓர் அட்டவணை.
குறைபாடு: மிகைமை

location அட்டவணையில் (location_key, street, city, province_or_state, country) உள்ளன. Vancouver, Victoria இரண்டும் கனடாவின் British Columbia-வில் உள்ளதால், "British Columbia, Canada" பல வரிசைகளில் மீண்டும் வருகிறது:

(…, Vancouver, British Columbia, Canada) (…, Victoria, British Columbia, Canada)

3Snowflake schema

பிரிக்கப்பட்ட Dimension அட்டவணைகள்

Dimension table-ஐ மேலும் சிறு tables-ஆகப் பிரித்தால் Snowflake. Product category விவரத்தை தனியாக வைத்தால் redundancy குறையலாம்; ஆனால் கூடுதல் joins தேவைப்படலாம். இது Star-ஐவிட அதிக normalisation கொண்டது.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

Snowflake-இல் dimension hierarchy தனித் tables-ஆக normalise செய்யப்படும்: product→category→department. Redundancy குறையலாம்; joins அதிகரிக்கும். Fact table பல இருப்பது Snowflake-இன் அடையாளமல்ல. பல fact tables shared dimensions பயன்படுத்துவது constellation-க்கான கருத்து.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Snowflake dimension tables normalise செய்கிறது: item→supplier; location→city. Repeated state/country data குறையும்; maintenance சீராகலாம்; queries-க்கு joins அதிகரிக்கும். அதனால் எல்லா databases-லும் எப்போதும் slower அல்லது storage saving negligible என்ற universal rule இல்லை; workload/engine/size பார்க்கவேண்டும்.

A star schema whose dimension tables are normalised (split into extra tables). The diagram branches out like a snowflake.

  • Example (Figure 6-2):
  • item → item(item_key, item_name, brand, type, supplier_key) + supplier(supplier_key, supplier_type)
  • location → location(location_key, street, city_key) + city(city_key, city, province_or_state, country)

Advantages

  • Reduces redundancy (normalised)
  • Easy to maintain
  • Saves storage space

Disadvantages

  • The space saved is negligible compared with the size of the fact table
  • More joins are needed per query, so browsing is less effective (slower)
Which is more popular?

The star schema is more popular than the snowflake, because query speed matters more than the small storage saving.

பரிமாண அட்டவணைகள் இயல்பாக்கப்பட்ட நட்சத்திரத் திட்டவடிவம் (கூடுதல் அட்டவணைகளாகப் பிரிக்கப்பட்டவை). வரைபடம் பனித்துகள் போன்று கிளைக்கிறது.

  • எடுத்துக்காட்டு (படம் 6-2):
  • item → item(item_key, item_name, brand, type, supplier_key) + supplier(supplier_key, supplier_type)
  • location → location(location_key, street, city_key) + city(city_key, city, province_or_state, country)

நன்மைகள்

  • மிகைமையைக் குறைக்கிறது (இயல்பாக்கப்பட்டது)
  • பராமரிக்க எளிது
  • சேமிப்பிடத்தைச் சேமிக்கிறது

தீமைகள்

  • உண்மை அட்டவணையின் அளவுடன் ஒப்பிடும்போது சேமிக்கப்படும் இடம் மிகச்சிறியது
  • ஒவ்வொரு வினவலுக்கும் அதிக இணைப்புகள் தேவை; எனவே உலாவல் குறைந்த திறனுடையது (மெதுவானது)
எது அதிகம் பிரபலமானது?

சிறிய சேமிப்பு மிச்சத்தைவிட வினவல் வேகம் முக்கியமானதால், பனித்துகளைக் காட்டிலும் நட்சத்திரத் திட்டவடிவம் அதிகம் பிரபலமானது.

4Fact constellation (galaxy schema)

பல Fact அட்டவணைகளின் இணைப்பு

Sales, Shipping போன்ற பல Fact tables ஒரே Time அல்லது Product dimensions-ஐப் பகிர்ந்தால் Galaxy schema. ஒரு business process-க்கு மட்டும் analysis கட்டுப்படாது; பொதுவான dimensions பொருந்த வேண்டும்.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Galaxy/constellation=பல fact tables சில dimensions பகிர்தல். Sales fact time/item/branch/location; shipping fact time/item/shipper/from_location/to_location. Time/item/location shared definitions report consistency-க்கு உதவும். Location ஒரே dimension-ஐ from/to என்ற இரு roles-இல் பயன்படுத்தலாம். ஒரே star-இல் ஒரு dimension split செய்தது snowflake; இரண்டாவது fact சேர்த்த shared stars constellation.

Multiple fact tables that share dimension tables. It is a collection of stars, hence also called a galaxy schema.

Example (Figure 6-3): two fact tables.

Fact table Keys (dimensions) Measures
sales time, item, branch, location dollars_sold, units_sold
shipping item, time, shipper, from_location, to_location dollars_cost, units_shipped

time, item and location are shared between both fact tables.

Exam focus

"Compare star, snowflake and fact constellation schemas" with diagrams is a favourite question. Draw the sales example for each. For snowflake show item → supplier and location → city. For constellation show sales + shipping sharing time/item/location.

பரிமாண அட்டவணைகளைப் பகிரும் பல உண்மை அட்டவணைகள். இது நட்சத்திரங்களின் தொகுப்பாக இருப்பதால் விண்மீன்பேரடைத் திட்டவடிவம் என்றும் அழைக்கப்படுகிறது.

எடுத்துக்காட்டு (படம் 6-3): இரு உண்மை அட்டவணைகள்.

உண்மை அட்டவணை சாவிகள் (பரிமாணங்கள்) அளவைகள்
sales time, item, branch, location dollars_sold, units_sold
shipping item, time, shipper, from_location, to_location dollars_cost, units_shipped

இரு உண்மை அட்டவணைகளும் time, item, location ஆகியவற்றைப் பகிர்கின்றன.

Exam focus

வரைபடங்களுடன் "நட்சத்திரம், பனித்துகள், உண்மை விண்மீன்கூட்டத் திட்டவடிவங்களை ஒப்பிடுக" என்பது விருப்பமான கேள்வி. ஒவ்வொன்றுக்கும் sales எடுத்துக்காட்டை வரையவும். பனித்துகளில் item → supplier, location → city ஆகியவற்றைக் காட்டவும். விண்மீன்கூட்டத்தில் sales + shipping, time/item/location-ஐப் பகிர்வதைக் காட்டவும்.

5Data warehouse vs data mart

Warehouse மற்றும் Data mart

முழு நிறுவனத்தின் விரிவான தகவல் Warehouse-இல் இருக்கும். Sales போன்ற ஒரு பிரிவிற்கான குறுகிய தகவல் Data mart. Mart சிறியது என்பதாலே அதன் தகவல் தானாகச் சரியாகிவிடாது.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Warehouse enterprise subjects across departments; mart குறிப்பிட்ட department/process-க்கான focused subset/view/store. Dependent mart warehouse-இலிருந்து; independent mart பிற sources-இலிருந்தும் உருவாகலாம். Scope வேறுபாடுதான் முக்கியம்; GB அளவு/build time மட்டும் definition அல்ல. Enterprise warehouse ஒரே central fact table என்ற அவசியமும் இல்லை.

Data warehouse Data mart
Scope Enterprise-wide: subjects across the whole organisation (customers, items, sales, assets, personnel) Department/process-focused: may be a dependent warehouse subset or an independent mart
Subjects Multiple, interrelated Selected / single subjects
Schema commonly used Fact constellation (models multiple interrelated subjects) Star or snowflake (single subject); star is more popular and efficient
Data sources Many Few
Size Large (100 GB – TB+) Smaller
Build time Months to years Weeks to months
Picture it

The warehouse is the central store of a supermarket chain. A data mart is the marketing department's shelf holding just the subjects it needs.

தரவுக் கிடங்கு தரவுச் சந்தை
நோக்கெல்லை நிறுவனம் முழுவதும்: முழு நிறுவனத்திலும் உள்ள பொருள்கள் (வாடிக்கையாளர்கள், பொருட்கள், விற்பனை, சொத்துகள், பணியாளர்கள்) துறை/செயல்முறையை மையமாகக் கொண்டது: கிடங்கைச் சார்ந்த உட்கணமாகவோ சுயாதீனச் சந்தையாகவோ இருக்கலாம்
பொருள்கள் பல, ஒன்றோடொன்று தொடர்புடையவை தேர்ந்தெடுக்கப்பட்ட / ஒற்றைப் பொருள்கள்
பொதுவாகப் பயன்படும் திட்டவடிவம் உண்மை விண்மீன்கூட்டம் (பல தொடர்புடைய பொருள்களை மாதிரியாக்குகிறது) நட்சத்திரம் அல்லது பனித்துகள் (ஒரு பொருள்); நட்சத்திரம் அதிகம் பிரபலமானதும் திறனுடையதும்

உருவாக்க நேரம் மாதங்கள் முதல் ஆண்டுகள் வரை வாரங்கள் முதல் மாதங்கள் வரை
கற்பனை செய்து பாருங்கள்

கிடங்கு என்பது பேரங்காடிச் சங்கிலியின் மையச் சேமிப்பகம். தரவுச் சந்தை என்பது தேவையான பொருள்களை மட்டும் கொண்ட சந்தைப்படுத்தல் துறையின் அலமாரி.

6Defining cubes with DMQL

DMQL-இல் Cube வரையறை

எந்த measures, dimensions கொண்டு cube அமைக்க வேண்டும் என்பதை DMQL மூலம் சொல்வோம். Code-ஐ மனப்பாடம் செய்வதற்கு முன் ஒவ்வொரு dimension எந்தக் கேள்விக்குப் பதில் தருகிறது என்று புரிந்துகொள்ளுங்கள்.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

DMQL-இல் cube பெயர், dimensions, measures தனித்தனியாக வரையறுக்கப்படுகின்றன. Dimension-இன் நிலைகள் என்ன, fact-இல் key எது, sum/count measure எது என code-ஐ வாசியுங்கள். SQL SELECT result-ஐ மட்டும் cube schema எனக் கொள்ள வேண்டாம். ஒரே measure அனைத்திலும் sum செய்யலாமா என்பதும் business meaning-ஐப் பொறுத்தது; balance போன்ற measure-கள் நேரம் முழுவதும் additive அல்லாமல் இருக்கலாம்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

DMQL course notation: define cube பெயர்[dimensions]:measures; define dimension பெயர் as(attributes). Star flat list; snowflake supplier(…) போன்ற nested subdimension; constellation “as time in cube sales” மூலம் reuse. இது இந்தப் பாடத்தின் language example; எல்லா DBMS-லும் run ஆகும் SQL standard அல்ல. count(*) rows எண்ணும்; sum(units_sold) quantities கூட்டும் — ஒவ்வொரு row ஒரு unit என்ற assumption இல்லாமல் இரண்டையும் ஒன்றாகக் கருதாதீர்கள்.

A Data Mining Query Language (DMQL) specifies mining tasks the way SQL specifies relational queries. Warehouses and marts are defined with two primitives:

define cube <cube_name> [<dimension_list>]: <measure_list>
define dimension <dimension_name> as (<attribute_or_subdimension_list>)

Star schema in DMQL

define cube sales_star [time, item, branch, location]:
    dollars_sold = sum(sales_in_dollars), avg_sales = avg(sales_in_dollars),
    units_sold = count(*)
define dimension time     as (time_key, day, day_of_week, month, quarter, year)
define dimension item     as (item_key, item_name, brand, type, supplier_type)
define dimension branch   as (branch_key, branch_name, branch_type)
define dimension location as (location_key, street, city, province_or_state, country)

In this course DMQL notation, define cube specifies the central cube/fact model (4 dimensions plus measures). This is not portable SQL syntax. count(*) counts rows, not quantities unless the grain is one unit per row. Each define dimension creates one dimension table.

Snowflake schema in DMQL

The only change is that sub-dimensions are nested inside the parent dimension:

define dimension item as (item_key, item_name, brand, type,
                          supplier(supplier_key, supplier_type))
define dimension location as (location_key, street,
                          city(city_key, province_or_state, country))

Defining supplier inside item implicitly creates a supplier_key in the item table. city inside location implicitly creates a city_key.

Fact constellation in DMQL

Define the sales cube as in the star schema, then define shipping and reuse the shared dimensions:

define cube shipping [time, item, shipper, from_location, to_location]:
    dollar_cost = sum(cost_in_dollars), unit_shipped = count(*)
define dimension time  as time in cube sales
define dimension item  as item in cube sales
define dimension shipper as (shipper_key, shipper_name,
                             location as location in cube sales, shipper_type)
define dimension from_location as location in cube sales
define dimension to_location   as location in cube sales

"as … in cube sales" is how a dimension is shared between fact tables.

Spot the difference fast
  • Star: flat attribute lists
  • Snowflake: nested brackets, supplier(…) and city(…)
  • Constellation: two define cube statements plus … in cube sales

SQL தொடர்புநிலை வினவல்களைக் குறிப்பிடுவதுபோல, தரவுச் சுரங்க வினவல் மொழி (DMQL) சுரங்கப் பணிகளைக் குறிப்பிடுகிறது. கிடங்குகளும் சந்தைகளும் இரு அடிப்படைக் கூறுகளால் வரையறுக்கப்படுகின்றன:

define cube <cube_name> [<dimension_list>]: <measure_list>
define dimension <dimension_name> as (<attribute_or_subdimension_list>)

DMQL-இல் நட்சத்திரத் திட்டவடிவம்

define cube sales_star [time, item, branch, location]:
    dollars_sold = sum(sales_in_dollars), avg_sales = avg(sales_in_dollars),
    units_sold = count(*)
define dimension time     as (time_key, day, day_of_week, month, quarter, year)
define dimension item     as (item_key, item_name, brand, type, supplier_type)
define dimension branch   as (branch_key, branch_name, branch_type)
define dimension location as (location_key, street, city, province_or_state, country)

இந்தப் பாடத்தின் DMQL குறியீட்டில் define cube, மையக் கனசதுர/உண்மை மாதிரியைக் குறிப்பிடுகிறது (4 பரிமாணங்களும் அளவைகளும்). இது பிற முறைமைகளில் அப்படியே பயன்படும் SQL தொடரமைப்பு அல்ல. count(*) வரிசைகளை எண்ணுகிறது; ஒரு வரிசைக்கு ஓர் அலகு என்ற நுணுக்கநிலை இருந்தாலன்றி பொருள் அளவுகளை அல்ல. ஒவ்வொரு define dimension-உம் ஒரு பரிமாண அட்டவணையை உருவாக்குகிறது.

DMQL-இல் பனித்துகள் திட்டவடிவம்

மாற்றம் ஒன்றே: பெற்றோர் பரிமாணத்துக்குள் துணைப் பரிமாணங்கள் உள்ளடக்கப்படுகின்றன:

define dimension item as (item_key, item_name, brand, type,
                          supplier(supplier_key, supplier_type))
define dimension location as (location_key, street,
                          city(city_key, province_or_state, country))

item-க்குள் supplier-ஐ வரையறுப்பது item அட்டவணையில் supplier_key-ஐ மறைமுகமாக உருவாக்குகிறது. location-க்குள் city என்பது city_key-ஐ மறைமுகமாக உருவாக்குகிறது.

DMQL-இல் உண்மை விண்மீன்கூட்டம்

நட்சத்திரத் திட்டவடிவத்தைப் போல sales கனசதுரத்தை வரையறுத்து, பின்னர் shipping-ஐ வரையறுத்துப் பகிரப்பட்ட பரிமாணங்களை மீண்டும் பயன்படுத்தவும்:

define cube shipping [time, item, shipper, from_location, to_location]:
    dollar_cost = sum(cost_in_dollars), unit_shipped = count(*)
define dimension time  as time in cube sales
define dimension item  as item in cube sales
define dimension shipper as (shipper_key, shipper_name,
                             location as location in cube sales, shipper_type)
define dimension from_location as location in cube sales
define dimension to_location   as location in cube sales

"as … in cube sales" மூலமே உண்மை அட்டவணைகளுக்கிடையே பரிமாணம் பகிரப்படுகிறது.

வேறுபாட்டை விரைவாகக் கண்டறியவும்
  • நட்சத்திரம்: தட்டையான பண்புக்கூறுப் பட்டியல்கள்
  • பனித்துகள்: உள்ளடக்கப்பட்ட அடைப்புக்குறிகள், supplier(…), city(…)
  • விண்மீன்கூட்டம்: இரு define cube கூற்றுகளும் … in cube sales என்பதும்

7Concept hierarchies

கருத்துகளின் படிநிலை

நாள் → மாதம் → ஆண்டு என ஒரே dimension-இல் பல levels இருக்கும். சிறிய நிலையிலிருந்து பெரிய நிலைக்கு roll-up செய்தால் மொத்தப் போக்கு தெரியும். Drill-down எதிர்த்திசையில் நுணுக்கத்தைக் காட்டும்.

மேலும் புரிந்துகொள்ள · தேர்வுக் குறிப்புகள்

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Street→city→province/state→country→all என்பது low→high hierarchy. Roll-up உயர் concept; drill-down detail. ஒரே attribute-க்கு வேறு business hierarchy இருக்கலாம் (calendar/fiscal time). Functional relationships சரியா சோதிக்கவும்; எல்லா நகரப் பெயரும் உலகளவில் unique அல்ல. ஒரு level பெயரை மட்டும் காட்டாமல் அது எந்த higher member-க்கு map ஆகிறது குறிப்பிடவும்.

A concept hierarchy is a sequence of mappings from low-level concepts to higher-level, more general concepts.

Location hierarchy (Figure 6-4)

              ┌──────────┴──────────┐
           Canada                  USA
       ┌──────┴──────┐        ┌─────┴──────┐

       │              │        │            │
   Vancouver      Toronto   New York     Chicago

city → province_or_state → country → all

  • Many hierarchies are implicit in the schema. If location has attributes number, street, city, province_or_state, zip_code and country, a total order gives: street < city < province_or_state < country (Figure 6-5).
  • Roll-up climbs the hierarchy (city → country). Drill-down goes back down.

  • பல படிநிலைகள் திட்டவடிவத்தில் மறைமுகமாக உள்ளன. location-க்கு number, street, city, province_or_state, zip_code, country ஆகிய பண்புக்கூறுகள் இருந்தால், முழுமையான வரிசை தருவது: street < city < province_or_state < country (படம் 6-5).
  • மேல்சுருக்கம் படிநிலையில் ஏறுகிறது (நகரம் → நாடு). கீழ்விரிப்பு மீண்டும் கீழே செல்கிறது.

9Quick revision sheet

விரைவாக நினைவுபடுத்திக்கொள்ள

Warehouse schema ஏன் வேறு?

Analysis-இல் பல rows-ஐச் சேர்த்து sums, comparisons செய்வோம். அதற்காக facts மற்றும் dimensions-ஐ ஒழுங்குபடுத்துகிறோம். Transaction database-இன் வடிவமே எல்லா analysis-க்கும் வேகமாக இருக்கும் என்று கருதக்கூடாது.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Warehouse analysis-க்கு fact+dimensions கொண்ட multidimensional schema எளிய group-by/join செய்ய உதவும். Star, snowflake, constellation மூன்று designs. ER என்பது operational modelling-இல் பொதுவானது; warehouse-இல் ER “பயன்படுத்தவே முடியாது” அல்ல. Data grain, relationships, query needs அடிப்படையில் schema தேர்வு செய்யப்படுகிறது.

நட்சத்திர வடிவத் தரவு அமைப்பு

நடுவில் விற்பனை போன்ற Fact table; அதைச் சுற்றி Time, Product, Customer போன்ற Dimension tables. நட்சத்திரம்போல் தோன்றுவதால் Star schema. Fact table-இல் measures மற்றும் dimension keys இருக்கும்.

Fact table-இல் foreign keys மற்றும் numerical measures இருக்கும். Dimension table-இல் descriptive attributes. Grain “ஒரு product ஒரு shop-இல் ஒரு நாளின் sales” என்றால் ஒவ்வொரு row அதையே பிரதிநிதித்துவப்படுத்த வேண்டும். Star dimension denormalised ஆக இருப்பதால் fewer joins, எளிய queries கிடைக்கலாம்; repeated descriptions சேமிப்பை அதிகரிக்கலாம்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Star-இல் நடுவில் sales fact: time_key,item_key,branch_key,location_key + dollars_sold/units_sold. ஒவ்வொரு dimension-க்கும் ஒரே denormalised table. Location-இல் city/state/country மீண்டும் வருவதால் redundancy; joins எளிதாகலாம். Diagram-இல் keys/facts மற்றும் descriptive attributes வேறுபடுத்துங்கள்.

பிரிக்கப்பட்ட Dimension அட்டவணைகள்

Dimension table-ஐ மேலும் சிறு tables-ஆகப் பிரித்தால் Snowflake. Product category விவரத்தை தனியாக வைத்தால் redundancy குறையலாம்; ஆனால் கூடுதல் joins தேவைப்படலாம். இது Star-ஐவிட அதிக normalisation கொண்டது.

Snowflake-இல் dimension hierarchy தனித் tables-ஆக normalise செய்யப்படும்: product→category→department. Redundancy குறையலாம்; joins அதிகரிக்கும். Fact table பல இருப்பது Snowflake-இன் அடையாளமல்ல. பல fact tables shared dimensions பயன்படுத்துவது constellation-க்கான கருத்து.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Snowflake dimension tables normalise செய்கிறது: item→supplier; location→city. Repeated state/country data குறையும்; maintenance சீராகலாம்; queries-க்கு joins அதிகரிக்கும். அதனால் எல்லா databases-லும் எப்போதும் slower அல்லது storage saving negligible என்ற universal rule இல்லை; workload/engine/size பார்க்கவேண்டும்.

பல Fact அட்டவணைகளின் இணைப்பு

Sales, Shipping போன்ற பல Fact tables ஒரே Time அல்லது Product dimensions-ஐப் பகிர்ந்தால் Galaxy schema. ஒரு business process-க்கு மட்டும் analysis கட்டுப்படாது; பொதுவான dimensions பொருந்த வேண்டும்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Galaxy/constellation=பல fact tables சில dimensions பகிர்தல். Sales fact time/item/branch/location; shipping fact time/item/shipper/from_location/to_location. Time/item/location shared definitions report consistency-க்கு உதவும். Location ஒரே dimension-ஐ from/to என்ற இரு roles-இல் பயன்படுத்தலாம். ஒரே star-இல் ஒரு dimension split செய்தது snowflake; இரண்டாவது fact சேர்த்த shared stars constellation.

Warehouse மற்றும் Data mart

முழு நிறுவனத்தின் விரிவான தகவல் Warehouse-இல் இருக்கும். Sales போன்ற ஒரு பிரிவிற்கான குறுகிய தகவல் Data mart. Mart சிறியது என்பதாலே அதன் தகவல் தானாகச் சரியாகிவிடாது.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Warehouse enterprise subjects across departments; mart குறிப்பிட்ட department/process-க்கான focused subset/view/store. Dependent mart warehouse-இலிருந்து; independent mart பிற sources-இலிருந்தும் உருவாகலாம். Scope வேறுபாடுதான் முக்கியம்; GB அளவு/build time மட்டும் definition அல்ல. Enterprise warehouse ஒரே central fact table என்ற அவசியமும் இல்லை.

DMQL-இல் Cube வரையறை

எந்த measures, dimensions கொண்டு cube அமைக்க வேண்டும் என்பதை DMQL மூலம் சொல்வோம். Code-ஐ மனப்பாடம் செய்வதற்கு முன் ஒவ்வொரு dimension எந்தக் கேள்விக்குப் பதில் தருகிறது என்று புரிந்துகொள்ளுங்கள்.

DMQL-இல் cube பெயர், dimensions, measures தனித்தனியாக வரையறுக்கப்படுகின்றன. Dimension-இன் நிலைகள் என்ன, fact-இல் key எது, sum/count measure எது என code-ஐ வாசியுங்கள். SQL SELECT result-ஐ மட்டும் cube schema எனக் கொள்ள வேண்டாம். ஒரே measure அனைத்திலும் sum செய்யலாமா என்பதும் business meaning-ஐப் பொறுத்தது; balance போன்ற measure-கள் நேரம் முழுவதும் additive அல்லாமல் இருக்கலாம்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

DMQL course notation: define cube பெயர்[dimensions]:measures; define dimension பெயர் as(attributes). Star flat list; snowflake supplier(…) போன்ற nested subdimension; constellation “as time in cube sales” மூலம் reuse. இது இந்தப் பாடத்தின் language example; எல்லா DBMS-லும் run ஆகும் SQL standard அல்ல. count(*) rows எண்ணும்; sum(units_sold) quantities கூட்டும் — ஒவ்வொரு row ஒரு unit என்ற assumption இல்லாமல் இரண்டையும் ஒன்றாகக் கருதாதீர்கள்.

கருத்துகளின் படிநிலை

நாள் → மாதம் → ஆண்டு என ஒரே dimension-இல் பல levels இருக்கும். சிறிய நிலையிலிருந்து பெரிய நிலைக்கு roll-up செய்தால் மொத்தப் போக்கு தெரியும். Drill-down எதிர்த்திசையில் நுணுக்கத்தைக் காட்டும்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Street→city→province/state→country→all என்பது low→high hierarchy. Roll-up உயர் concept; drill-down detail. ஒரே attribute-க்கு வேறு business hierarchy இருக்கலாம் (calendar/fiscal time). Functional relationships சரியா சோதிக்கவும்; எல்லா நகரப் பெயரும் உலகளவில் unique அல்ல. ஒரு level பெயரை மட்டும் காட்டாமல் அது எந்த higher member-க்கு map ஆகிறது குறிப்பிடவும்.

Weka Explorer-ஐப் பயன்படுத்துதல்

முதலில் dataset, attributes, missing values, class தேர்வைப் பாருங்கள். Preprocess, Classify, Cluster tabs வெவ்வேறு வேலைகள் செய்கின்றன. தவறான class தேர்வு செய்தால் வேறு கேள்விக்கான model கிடைக்கும்.

விரிவான விளக்கம் · கணக்கும் தேர்வுப் புள்ளிகளும்

Explorer Preprocess: ARFF open→instances(rows)/attributes(columns) எண்ணிக்கை→type/missing/distribution/histogram→தேவையான filter. Class selector-இல் predict செய்யவேண்டிய target சரியா பார்க்கவும்; last column default ஆக இருக்கலாம், அது அவசியமான விதி அல்ல. Other tabs Classify/Cluster/Associate/Select attributes/Visualize. Save/edited data மற்றும் filter choices-ஐ பதிவு செய்யவும்.
