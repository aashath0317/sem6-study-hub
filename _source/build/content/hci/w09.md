## Task analysis & cognitive modelling

- **Task analysis** is the formal breakdown of **what a user must do** (physical actions and cognitive processing) to reach a desired system state.
- **Cognitive modelling** predicts **how a person's mind works while using a particular UI**: how they'd complete a task with that specific interface [[01:01]].

:::key Why model instead of test? [[02:46]]
- Models **don't need to be implemented or prototyped**. You predict and assess mentally, **without real users**.
- They have **explanatory power** (theory explains behaviour) and give a **foundation for design**, as in other engineering fields.
- You can **calculate performance times** and compare workflows **before writing code**.
:::

:::grid
**🖥 Information processor model**

Human = input–output unit (the **Model Human Processor**, MHP). Focuses on **keystrokes, pointing and perceptual cycles**: GOMS, KLM.
+++
**🧠 Cognitive / predictor model**

Focuses on **mental simulations**, hypotheses, problem-solving strategies and forming intentions.
:::

### The model family [[04:09]]

| Model | Level | What it does |
|---|---|---|
| **GOMS** | **Higher, abstract**: the **umbrella**; structured and hierarchical like HTA | Goals, Operators, Methods, Selection rules |
| **KLM** | **Lowest, operational** | Times individual keystrokes, pointing, clicks |
| **Fitts's law** | Motor | Time to **reach and act on a target** |
| **MHP** (Model Human Processor) | Underlying | The model of human cognition beneath all of these |

The roots are **1970s–80s theory** (Card, Moran & Newell) [[02:00]].

## The GOMS framework

**GOMS** (Card, Moran & Newell) models an expert doing **goal-oriented, error-free** tasks:

| Letter | Component | Meaning | Example: send a report to your manager |
|---|---|---|---|
| **G** | **Goals** | The high-level objective | "Send an official report to the manager" |
| **O** | **Operators** | **Elementary** perceptual, motor or cognitive actions | Click a button, type a key, scan a list |
| **M** | **Methods** | **Ordered sequences of operators** that achieve a (sub)goal | Method A: email · Method B: chat app |
| **S** | **Selection rules** | **If-then logic** choosing which method to use | IF formal or urgent THEN email ELSE chat |

<figure><img src="Figure%209.1.PNG" alt="GOMS methods and selection rules"><figcaption>Figure 9.1: Methods and selection rules branching from a goal</figcaption></figure>

```
GOAL: Send report to manager
 ├─ [Selection rule] IF formal THEN use METHOD-A ELSE METHOD-B
 ├─ METHOD-A (Email):  open mail → click Compose → type address → attach file → click Send
 └─ METHOD-B (Chat):   open chat → find manager → drag file in → press Enter
```

## Keystroke-Level Model (KLM)

KLM is a **simplified, quantitative version of GOMS**. It calculates the **execution time for an expert doing a routine task with no errors**:

:::formula
T<sub>execute</sub> = T<sub>K</sub> + T<sub>P</sub> + T<sub>H</sub> + T<sub>D</sub> + T<sub>M</sub> + T<sub>R</sub>
:::

| Operator | Meaning | Typical time |
|---|---|---|
| **K** | **Keystroke** / button press | ~**0.20 s** (skilled typist 0.12 s, novice 0.40 s) |
| **P** | **Pointing** the mouse at a target | ~**1.10 s** |
| **H** | **Homing**: moving the hand between keyboard and mouse | ~**0.40 s** |
| **M** | **Mental preparation** before the next chunk | ~**1.35 s** (the largest) |
| **D** | **Drawing** with pen or mouse | Depends on the domain |
| **R** | **System response** time (waiting) | Depends on the system |

:::warn Where to put M operators [[v4 00:00]]
**Insert an M before every P that selects a command.** You must mentally prepare before every choice. M is the **biggest** operator, so **too many commands to choose from means too many M's**, which makes the task slow [[v4 01:04]]. Each operator time is an **estimate**; add them up for the total task time.
:::

## Fitts's law

**Fitts's law** comes from product ergonomics and is easily adapted to UIs. It predicts the **time to move a pointer (or finger) to a target** [[v4 03:38]].

:::formula
**MT = a + b · log₂(2D / W)**   (PDF form)
**MT = a + b · log₂(D / W + 1)**   (Shannon form, used in the lecture video [[v4 05:47]])
:::

| Symbol | Meaning |
|---|---|
| **MT** | Movement time |
| **D** | **Distance** (amplitude) to the target |
| **W** | **Width** of the target along the direction of movement |
| **a, b** | Constants from **linear regression**: a = intercept, b = slope |
| **log₂(2D/W)** | **Index of Difficulty (ID)** in bits |

:::key In plain words [[v4 06:44]]
**Longer distance + smaller target = more time.** The wider the target, the less time it takes; the narrower, the more.
:::

### What Fitts's law means for design

| Implication | Explanation |
|---|---|
| 🎯 **Make important targets big** | Larger W means a faster click. **Primary call-to-action** buttons need generous hit areas. On phones, the **answer and end-call buttons are large** [[v4 07:51]] |
| 📏 **Keep small targets close** | If a target must be narrow, **reduce the distance**, which also cuts errors |
| 🖥 **Use screen edges and corners** | Edges have **effectively infinite width** (W = ∞), because the cursor stops at the edge: Windows **Start** menu, Mac **Apple menu** |
| ⚖️ **Speed–accuracy trade-off** | Fast movement + small targets = **higher error rates** [[v4 06:44]] |
| ⚡ **Scope** | Applies to **rapid pointing movements**, not continuous movements [[v4 08:58]] |

## Strengths and limits of predictive models

:::grid
**✅ Strengths**

- **Objective, repeatable** numbers to compare prototypes
- **Saves time and money**: finds bottlenecks **before** user testing
- Breaks complex tasks into **measurable micro-steps**
+++
**⚠️ Limitations**

- Assumes **expert, error-free** performance. **No novice confusion, slips or exploring**
- Ignores **fatigue, stress, emotion, delight, creativity**
- Hard to use when goals are **unstructured or keep changing**
:::
